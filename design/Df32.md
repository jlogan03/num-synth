# Df32: extended precision using two f32 values

Status: implemented in `src/df32.rs`, with exact-reference property tests and
a CPU benchmark harness. Embedded and WebAssembly builds are checked; GPU
execution and target-specific performance remain unvalidated.

## Purpose

`Df32` represents one number as a leading `f32` plus an `f32` residual. The
name identifies the component type; storage occupies 64 bits. The established
names for this technique are double-single and float-float arithmetic.

The goal is useful additional resolution in general numerical computation on
embedded devices and GPUs whose native single-precision arithmetic is fast.
An important workload is preserving relative positions of micron-scale
features in structures about 10 meters across. Each value carries its own
residual; values need not share an origin.

We want as much accuracy as this small representation can deliver with fixed,
short operation sequences. We do not require binary64 accuracy or range,
correctly rounded pair results for every operation, exact expression
evaluation, or a growing accumulator. Accuracy must be characterized per
operation rather than inferred from the storage size. Performance choices
must preserve documented invariants and must not silently change semantics
between builds or input magnitudes.

The runtime is unconditionally `no_std`, uses no `alloc`, and requires no
global allocator. Working arithmetic uses `f32`, including explicit hardware
FMA where required. There is no integer significand buffer, separate exponent,
dynamic storage, convergence loop, or runtime precision setting.

## Representation and normalization

Rust layout, with private fields:

```rust
#[repr(C)]
#[derive(Clone, Copy, Debug)]
pub struct Df32 {
    hi: f32,
    lo: f32,
}
```

For finite values, the mathematical value is the **unevaluated real sum**
`hi + lo`. Evaluating that expression in `f32` would discard the extra detail.
Both components may be signed. There is no separate result/status wrapper;
the existing floating-point encodings represent zero, infinity, and NaN.

The normalized finite invariant is:

1. `hi` is round-to-nearest, ties-to-even in binary32 of the represented sum.
2. `lo` is the remaining exact difference between that sum and `hi`.
3. A zero residual is stored as positive zero. A zero value has a zero high
   component and positive-zero low component; its sign lives in `hi`.

Consequently the components do not overlap in significance. Away from range
boundaries, `abs(lo) <= 0.5 * ulp(hi)` is a useful consequence, but that inequality
alone is not the definition: midpoint ties and asymmetric spacing at powers
of two also matter. `TwoSum` supplies the normalization, including when
cancellation makes the residual larger than the provisional high component.

For a representable finite real sum these rules fix the pair, apart from
the deliberate distinction between signed zeros. Public component access is
read-only; construction from two components normalizes their sum. A normalized
pair may have a very large exponent gap and still retain its tiny residual.
It is not a uniform 48-bit floating-point lattice.

The target size is eight bytes, with the alignment of `f32`. A shader binding
may impose additional alignment or array stride, so its buffer layout must be
checked separately. Transport the two components explicitly; never collapse
them to one `f32` before transferring them to the device.

## Resolution and the motivating workload

Ordinary normalized values have roughly 48 significant binary bits, about
14 decimal digits, rather than binary64's 53 bits. This is a working estimate,
not a universal relative-error bound for arithmetic or cancellation.

For a normal binary32 number in `[2^e, 2^(e+1))`, adjacent values are separated
by `2^(e-23)`. A nominal 48-bit significand would have spacing `2^(e-47)`:

| Magnitude, with meters as the unit | f32 spacing | Nominal 48-bit spacing |
| --- | --- | --- |
| 10 m | `2^-20 m`, about 0.954 micrometers | `2^-44 m`, about 0.057 picometers |
| 1,000,000 m | `2^-4 m`, 6.25 centimeters | `2^-28 m`, about 3.73 nanometers |

The second column explains the difficulty with a single `f32` near 10 meters:
a one-micron difference is only about one representable step. Some features
are distinguishable, but their relative positions are heavily quantized.
For example, rounding `10 + 0.000001` to `f32` and subtracting `10` gives
`0.00000095367431640625`, about 4.63% below one micron.

With Df32, adding a stored `1e-6_f32` offset to an exact `10` should retain the
offset in the pair; subtracting `10` should recover that input offset exactly
for this case. The offset itself differs from one mathematical micron by
about `2.52e-15` meters. This demonstrates the representation's margin for the
workload, without claiming that an arbitrary long computation keeps that error.

Input precision still matters. Expanding a coordinate that was already rounded
to a single `f32` cannot recover its lost detail. Build positions from coarse
and fine components, perform the preceding computation in Df32, or split a
higher-precision input at the host boundary. Keep the result paired until the
consumer no longer needs its fine detail.

## Range and accuracy limits

Df32 inherits binary32's exponent scale. The design does not attempt to exploit
the small possible extension beyond `f32::MAX` from a positive residual or to
rescue an overflowing high-component intermediate. Near underflow, the low
component progressively loses precision. With gradual underflow the smallest
positive component is `2^-149`; adding a second component cannot create values
below that quantum. There is no claim of doubled precision throughout the
subnormal range.

The primary accuracy domain is normalized finite inputs whose intermediate
operations stay in range and whose required residuals do not underflow. The
10-meter/micron workload is comfortably inside it. Extreme exponents, very
ill-conditioned problems, and long accumulation chains need separate error
analysis. A small relative error in a coordinate can still become a large
relative error in the difference between nearly equal coordinates.

Operations return normalized pairs, but they need not be the nearest possible
pair to the exact mathematical result. Do not round to a fictional fixed
48-bit grid. Keep every residual bit that the chosen sequence retains.

## Arithmetic primitives and execution semantics

In the pseudocode below, each ordinary operation is an individually rounded
binary32 operation using round-to-nearest, ties-to-even. `fma(a,b,c)` has one
rounding after the exact product and sum. These are finite-path algorithms;
exception handling is specified separately.

Use standard `TwoSum` for arbitrary magnitudes:

```text
two_sum(a, b):
    s = a + b
    v = s - a
    e = (a - (s - v)) + (b - v)
    return (s, e)
```

When its intermediates stay in range under the required floating-point
semantics, the returned real sum equals the exact input sum. It costs six
adds/subtracts. FastTwoSum costs three, but requires an established magnitude
condition such as `abs(a) >= abs(b)`. Use it only at a call site with a
documented proof for that algorithm, including cancellation cases. Do not
insert magnitude sorting and conditional branches merely to select it.

For multiplication, use the fused residual:

```text
two_prod(a, b):
    p = a * b
    e = fma(a, b, -p)
    return (p, e)
```

This recovers the exact product when the product and its residual are
representable and the operations do not overflow. Underflow can invalidate
that exactness. An ordinary multiply followed by add is not a replacement
for the explicitly fused operation.

The compiler must preserve the stated operation order: no reassociation,
unsafe fast-math, or implicit contraction across the error-recovery steps.
The scalar primitive is `libm::fmaf`, the same no-std implementation used by
`num-traits`. It is called directly so a consumer enabling `num-traits/std`
cannot change this library's primitive backend through feature unification.
Both runtime dependencies support no-std without allocation. `num-traits`
provides the `Zero`, `One`, `MulAdd`, and `MulAddAssign` integrations; the crate
does not claim the much larger `Float` interface without implementing it.

Backend selection is delegated to libm rather than implementing a second
software FMA. In libm 0.2.16, x86 uses a cached runtime hardware selection and
AArch64 has a hardware path; other targets can use a software fallback. That
fallback uses wider arithmetic internally, which can require software f64
helpers on an f32-only embedded target. This is a portability path, not a
performance claim. The Df32 kernels themselves contain only f32 arithmetic.
The inspected x86 benchmark assembly calls libm's FMA helper; these calls have
real overhead. A future shader backend must bind this primitive to a genuinely
fused device instruction and validate its semantics and generated code. Merely
compiling the Rust crate as no-std does not establish GPU performance.

Cross-backend consistency means the same finite result bits for the same
components and specified primitive sequence on conforming backends. A GPU
that flushes subnormals or relaxes arithmetic is not automatically conforming:
either configure the required semantics or document and validate a restricted
domain in which all needed intermediates satisfy them. The type alone cannot
override shader-language or hardware arithmetic rules.

## Initial arithmetic choices

These are the implemented baseline sequences. Each has a fixed
amount of work, with no allocation or data-dependent refinement. Lower-cost
alternatives need an error analysis and benchmark before replacing them.

### Addition and subtraction

Preserve errors from both component sums so cancellation of the high parts
does not unnecessarily discard the information held in the low parts:

```text
add(a, b):
    (s, e) = two_sum(a.hi, b.hi)
    (t, f) = two_sum(a.lo, b.lo)
    (h, l) = two_sum(s, e + t)
    return normalize(h, l + f)

sub(a, b):
    return add(a, negate(b))
```

`normalize` uses standard `TwoSum`, followed by the zero/special-value rules.
The finite addition sequence costs 26 adds/subtracts before any proven
FastTwoSum substitutions. The two ordinary correction additions can lose
information; this is not an exact four-term summation promise. Prefer this
explicit cancellation-aware baseline to choosing a cheaper addition solely
on an assumption that one partial sum must dominate another.

### Multiplication

```text
mul(a, b):
    (p, e) = two_prod(a.hi, b.hi)
    e = fma(a.hi, b.lo, e)
    e = fma(a.lo, b.hi, e)
    e = fma(a.lo, b.lo, e)
    return normalize(p, e)
```

This uses one multiply, four FMAs including product-error recovery, and six
adds/subtracts for normalization. Keep the low-by-low term initially: one
extra FMA is a small, measurable cost. Intermediate correction rounding means
the algorithm is not an exactly rounded multiplication of two pairs.

### Fused multiply-add

`a.mul_add(b, c)` computes the
pair-valued expression `a * b + c`, retaining product residuals until they have
been combined with the addend. It must not be implemented as `add(mul(a, b), c)`:
that would discard product information before cancellation with `c`.

The kernel decomposes all four component products and combines the leading
product with the high addend before accumulating the corrections:

```text
(p, e) = two_prod(a.hi, b.hi)
(s, t) = two_sum(p, c.hi)
(x, xe) = two_prod(a.hi, b.lo)
(y, ye) = two_prod(a.lo, b.hi)
(z, ze) = two_prod(a.lo, b.lo)
(h, l) = (e, 0)
for v in [t, c.lo, x, xe, y, ye, z, ze]:  # eight explicit calls in code
    (h, error) = two_sum(h, v)
    l = l + error
(hi, lo) = two_sum(s, h)
return normalize(hi, lo + l)
```

The correction state is two scalar temporaries, not a public Df32 value or a
variable-length expansion. The eight updates are explicitly unrolled. There
are four multiplies, four scalar FMAs, and 75 adds/subtracts before compiler
simplification, plus special-value guards. No magnitude sorting, convergence
loop, intermediate Df32 product, or heap storage is involved. Standard TwoSum
is used throughout.

An absolute forward-error bound explains the compensation. Let `u = 2^-24`
and `gamma8 = 8*u/(1-8*u)`. Assume each TwoProd/TwoSum is exact in its stated
domain, no overflow, and relative rounding bounds apply to the correction
additions. If `error_i` are the eight exact errors recovered by the correction
TwoSums, only accumulation of those errors loses information. Its absolute
error is at most `gamma8 * sum(abs(error_i))`. The final `lo + l` contributes
at most `u * abs(lo + l)` with the sum here interpreted exactly. Final
normalization is exact. Thus the combined absolute error is bounded by the
sum of these two quantities. Since the recovered errors are already small,
this is a second-order error in the ordinary domain. It is not a universal
relative-error bound on a nearly canceled final result. Subnormal rounding
requires absolute underflow terms instead of this relative model.

This extra compensation matters when `s` is zero: a single f32 sum of all
corrections would retain only single precision in the remaining value.

The contract is a combined operation without an intermediate product rounded
to Df32. Internal f32 operations still round, so final normalization alone
does not establish correctly rounded evaluation of the exact expression.
As with the other operators, validate and document the achieved accuracy;
do not claim IEEE-style single-rounding semantics for the pair without a
proof. Range limits remain explicit: the first implementation need not rescue
an overflowing component product through later cancellation.

### Division

Division uses one fixed quotient correction with the pair operations above:

```text
div(a, b):
    q0 = a.hi / b.hi
    r = sub(a, mul(b, from_f32(q0)))
    q1 = (r.hi + r.lo) / b.hi
    return normalize(q0, q1)
```

This intentionally favors a reusable baseline over an unverified optimized
remainder formula. It uses two scalar divisions, one pair multiplication,
one pair subtraction, and final normalization. There is no adaptive iteration.
Both this remainder and `(-b).mul_add(from_f32(q0), a)` pass the tested accuracy
target. The initial CPU microbenchmark shows the fused alternative costs more,
so division retains the separate remainder. There is no runtime selection of
algorithms. Revisit this choice if a target workload establishes a useful
accuracy or throughput benefit.

Unary negation changes both component signs, then restores a positive-zero
residual. Square root and transcendental functions are outside the initial
implementation. Both pair-valued multiply-add and hardware f32 FMA inside
the arithmetic algorithms are in scope.

## Special values and comparisons

Use a single canonical quiet NaN (`hi` bits `0x7fc00000`, `lo = +0`) and encode
infinities as `(infinity, +0)`. NaN payloads and signaling status are not part
of the contract. Arithmetic checks special inputs before running transforms
that would otherwise turn a valid infinity into NaN through `infinity-infinity`.

For NaN or infinite inputs, use the corresponding scalar operation on the
high components and canonicalize its result. Division by a zero pair follows
scalar division, including signed infinity or NaN. For finite inputs, a
nonfinite high sum, high product, or leading quotient is terminal and is
returned in canonical form; subsequent residual work must not corrupt it.
If later finite-path intermediates become nonfinite, canonicalize the result;
do not introduce exponent rescaling or an extended accumulator to recover it.
Underflow follows the specified primitive semantics and can lose the residual.

For pair-valued FMA, classify all three inputs before error recovery. Any NaN
input, zero times infinity, or an infinite product added to opposite infinity
produces canonical NaN; otherwise valid infinite results retain their sign.
Signed-zero behavior follows fused multiply-add under round-to-nearest,
ties-to-even. Test these cases separately from the finite accuracy domain.

Preserve scalar signs for input zeros and for zero multiplication/division
results. Exact cancellation in addition/subtraction produces positive zero,
except that adding two negative zeros retains negative zero. Implement these
rules explicitly where normalization would otherwise lose the sign. Special
handling should use short guards or selects as appropriate to the backend,
with an ordinary finite path that stays straight-line.

Comparison is numerical, not comparison after collapsing to `f32`. For
normalized non-NaN pairs, compare high components first and then low
components, treating signed zeros as equal. NaNs are unordered and unequal
to every value. Implement `PartialEq`/`PartialOrd`; do not derive comparisons
from raw bits or expose `Eq`/`Ord` as though NaN were an ordinary number.

## API and conversion boundaries

Initial surface: `Df32`, `from_f32`, `from_f64`, `from_parts`, `to_parts`,
`to_f32`, `to_f64`, classification methods, comparisons, and `+`, `-`, `*`,
`/`, unary `-` with their assignment forms, and `mul_add(self, b, c) -> Df32`.
Component fields remain private. Constants include zero, negative zero, one,
NaN, and both infinities. `From` conversions match the named conversions.

- `from_f32(x)` stores `(x, +0)` with special values canonicalized.
- `from_parts(hi, lo)` normalizes the real sum of two components; it does not
  trust callers to satisfy the FastTwoSum precondition.
- `to_parts()` returns the normalized pair for transport or inspection.
- `to_f32()` returns `hi`, the correctly rounded represented sum by the
  normalization invariant. It deliberately discards the residual.
- `from_f64(x)` splits at the boundary: first `h = x as f32`, then
  `l = (x - f64(h)) as f32`, then normalizes `(h, l)`. Handle overflow and
  special values before subtracting. This is a defined conversion sequence,
  not an exact binary64 round-trip or a universal nearest-pair promise.
- `to_f64()` evaluates `f64(hi) + f64(lo)`. It rounds the stored sum once to
  binary64; a pair with widely separated components need not fit exactly.

The f64 conversions are standalone boundary conveniences. Working arithmetic
must never call them or require native f64 instructions. There are no `_f64`
operation variants and no implicit conversions during expressions.

## Validation and performance acceptance

Tests verify invariants and the intended workload; stronger accuracy claims
need additional analysis. Host tests may use wider or exact
arithmetic independently of the allocation-free runtime. Native f64 is useful
in the ordinary domain but is not an exact oracle for every possible pair;
use exact dyadic or higher-precision references where needed.

Implemented coverage:

- TwoSum reconstruction and normalization, including arbitrary magnitude
  order, ties, power-of-two boundaries, cancellation, and subnormals.
- FMA product reconstruction in its exactness domain; explicit tests where
  residual underflow prevents exact reconstruction.
- Pair-valued FMA against an exact or higher-precision reference, including
  leading-product cancellation, cross-term and low-by-low contributions,
  special values, and range boundaries. Include cases where separate multiply
  and add lose a residual that the combined kernel must retain. Compare errors
  and cost with `a * b + c`, and validate its use in the division remainder.
- Normalized outputs and reference errors for every operator, mixed signs,
  near cancellation, exponent gaps, and fixed arithmetic chains. Record
  absolute error as well as relative error near zero.
- A directed 10-meter plus one-micron construction/subtraction example that
  recovers the input offset; sweeps of micron and submicron separations across
  positive and negative coordinates, plus scale/translate/inverse chains.
- As an initial application acceptance target, absolute separation error
  below one nanometer for those specified short chains around 10 meters.
  Document each chain, input precision, and conditioning. This is a test target
  to validate, not a guarantee for arbitrary programs or iteration counts.
- Conversion boundaries, NaNs, infinities, signed zeros, overflow/underflow,
  and comparison behavior. No universal f64 round-trip property.
- Debug and optimized host execution of the same reference tests. GPU
  execution of these vectors remains future backend validation, with any
  restricted exponent domain to be stated explicitly.

No-std compilation passes for `thumbv7em-none-eabihf` and
`wasm32-unknown-unknown`. These are compilation checks, not hardware execution. Enforce no allocation through
the runtime's dependencies and source, without allocator-counting tests.

Benchmark independent operations, dependency chains, and representative
relative-position workloads. Compare against native f32 and, where available,
native f64. Measure GPU throughput, register use, spills, and buffer bandwidth;
check the generated instructions for FMA lowering and hidden helper calls.
The pair doubles stored data compared with f32, and the arithmetic costs more
than one scalar instruction. Do not promise a speedup from instruction counts
alone or assume CPU and GPU rankings are the same.

The implementation covers representation, conversions, TwoSum/TwoProd,
addition/subtraction, multiplication, pair-valued FMA, and fixed-correction
division. Next work is target-specific primitive integration and measured
optimization. Every FastTwoSum replacement still needs its local precondition
documented beside the call.

Run `cargo test`, `cargo test --release`, `cargo clippy --all-targets -- -D warnings`,
`cargo fmt --check`, and `cargo bench --bench arithmetic`. The runtime dependency
tree contains only `num-traits` and `libm`; property testing and exact integer
references are development dependencies.

An initial x86-64 release run with libm 0.2.16 measured approximately 28 ns for
a dependent Df32 FMA, 24 ns for separate multiply/add, and 5 ns for native f32
or f64 FMA. The four-independent-values case took about 64 ns per iteration,
or 16 ns per value. The separate/fused division-remainder variants took about
34/37 ns. These are illustrative microbenchmark observations including harness
and call overhead, not stable latency guarantees or GPU predictions. Hardware
and compiler settings can change the ranking. The benchmark source is kept
in `benches/arithmetic.rs` so these choices can be revisited.

## Reference

Andrew Thall, [Extended-Precision Floating-Point Numbers for GPU Computation](https://andrewthall.org/papers/df64_qf128.pdf),
provides background on paired single-precision arithmetic and the TwoSum /
FastTwoSum distinction. Its `df64` terminology names the storage size; this
project deliberately uses `Df32` to name the component type. The operation
sequences and acceptance criteria above are this project's contract.

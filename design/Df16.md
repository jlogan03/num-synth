# Df16: extended precision using two f16 values

Status: implemented in `src/df16.rs`, with reference tests and all three CPU
benchmark harnesses. The `half` Cargo feature enables `#![feature(f16)]` on
nightly Rust and exposes `Df16`. Default builds remain stable-compatible.
The feature adds no dependency on the `half` crate; components use Rust's
primitive `f16`. GPU execution remains unvalidated.

## Purpose and scope

`Df16` represents one number as a leading binary16 value plus a binary16
residual. The name identifies the component type, as with [Df32](Df32.md).
Its purpose is to retain useful extra precision on devices with efficient
half-precision arithmetic using fixed storage and short operation sequences.

Get what this format can provide without compromising consistent semantics
or performance. There is no requirement to match Df32's application accuracy,
to meet a micron-scale position target, or to equal f32 precision or range.
Arithmetic need not produce the nearest possible pair. Measure the accuracy
of each chosen sequence and document where residuals disappear.

The runtime remains `no_std` and allocation-free. Arithmetic uses f16
primitives, including scalar FMA, and a fixed number of scalar temporaries.
There is no variable-length expansion, iterative refinement to convergence,
separate exponent, or exact arithmetic runtime. Wider scalar types are for
explicit conversions and test references, not implicit working arithmetic.

## Representation

Private storage:

```rust
#[repr(C, align(4))]
#[derive(Clone, Copy, Debug, Default)]
pub struct Df16([f16; 2]); // [hi, lo]
```

Size, alignment, and array stride are four bytes, verified by tests.
Shader buffer and argument layouts need separate validation.
Use component access for transport rather than collapsing the pair.

The value is the unevaluated real sum `hi + lo`. A finite normalized pair has:

1. `hi = RN16(hi + lo)`, with round-to-nearest, ties-to-even.
2. `lo` equal to the exact remaining difference from that high component.
3. Positive-zero `lo` whenever the residual is zero. For a zero value the
   sign is carried by `hi`.

Normalization is defined by the rounded sum, including midpoint parity and
asymmetric spacing at powers of two. A magnitude bound on the residual alone
does not define a canonical pair. Public `from_parts` normalizes arbitrary
component order; callers cannot mutate the stored components.

Infinities and NaNs use the existing f16 encodings with a positive-zero
residual. Use `f16::NAN` without specifying a NaN payload or sign. There is no
separate outcome/status type.

## Precision and range

Binary16 has 11 significant bits in normal values. Two normalized components
can provide roughly 22 significant bits when both components and the needed
intermediate residuals have adequate range. This estimate is neither a
uniform 22-bit lattice nor a universal arithmetic error bound. A large
exponent gap can preserve an unusually small residual, while underflow can
remove most of the expected gain.

Useful binary16 limits are:

| Quantity | Value |
| --- | --- |
| Largest finite component | 65,504 |
| Smallest positive normal component | `2^-14`, about `6.10e-5` |
| Smallest positive subnormal component | `2^-24`, about `5.96e-8` |
| Normal-range unit roundoff | `u = 2^-11` |
| Component spacing in binade `[2^e, 2^(e+1))` | `2^(e-10)` |
| Nominal 22-bit spacing in that binade | `2^(e-21)` |

Every finite pair is an integer multiple of `2^-24`; cancellation cannot
create a smaller nonzero value. A subnormal high component has no nonzero
normalized residual. For `abs(hi) < 2^-3`, even the largest admissible
residual is subnormal, so its precision is limited by that absolute quantum.
The gradual degradation therefore starts well before the high component
itself becomes subnormal. At the upper end, a residual can slightly extend
the finite sum beyond 65,504, but we do not exploit that as a larger guaranteed
range. Overflow of a leading arithmetic intermediate is terminal.

For scale, near 10 the f16 spacing is `2^-7` (0.0078125), and a nominal
22-bit spacing is `2^-18` (about 3.81 millionths). Very near the exact high
component 10, the residual can instead store multiples of `2^-24`. A stored
`1e-6` offset rounds to `17 * 2^-24`, about `1.013279e-6`: adding it to 10
and subtracting 10 can retain the stored offset, but cannot recover the
original decimal input. Away from that high component the residual spacing
can be much coarser. This illustrates the variable resolution, not an
application acceptance requirement.

Df16 occupies the same four bytes as f32, which has 24 significant bits and
a much wider exponent range. Df16 is not a general storage or accuracy
improvement over f32. Its potential value depends on actual half arithmetic
throughput and workloads benefiting from separately retained residuals.

## Primitive semantics

Every operation in the following sequences rounds to binary16 individually.
Require nearest-even rounding, gradual underflow for required subnormals,
and preservation of the written order. Do not enable reassociation,
algebraic/fast-math operations, or implicit contraction of error-recovery
steps. A compiler may lower an operation through wider hardware, but must
preserve these binary16 results.

Use standard TwoSum for arbitrary magnitudes:

```text
two_sum(a, b):
    s = a + b
    v = s - a
    e = (a - (s - v)) + (b - v)
    return (s, e)

two_prod(a, b):
    p = a * b
    return (p, fma(a, b, -p))
```

TwoSum is exact when its intermediates stay in range under these semantics.
TwoProd additionally needs its product residual to be representable; that
condition fails much more often in binary16 than binary32. A zero recovered
error does not prove the exact product had no residual.

The scalar FMA is a direct call to primitive `f16::mul_add`, with one
rounding of the exact product plus addend. Confirm no-std availability,
linking, and instruction lowering on each deployment target. Do not replace
it with ordinary multiply/add, or assume
an f32 FMA followed by an f16 cast has identical single-rounding semantics.
There is no custom software FMA or thin forwarding wrapper.

FastTwoSum saves three additions but requires `abs(a) >= abs(b)`. Use it
only where a local proof covers binary16 ties, cancellation, and underflow.
The implementation uses full TwoSum for arithmetic normalization; Df32's
optimized call sites are not an automatic license to substitute it here.

## Initial arithmetic sequences

These fixed-work baselines follow Df32. `normalize` uses TwoSum and then
applies the zero/special-value rules. Pseudocode describes finite paths;
preserve exceptional leading results as specified below.

```text
add(a, b):
    (s, e) = two_sum(a.hi, b.hi)
    (t, f) = two_sum(a.lo, b.lo)
    (h, l) = two_sum(s, e + t)
    return normalize(h, l + f)

sub(a, b):
    return add(a, negate(b))

mul(a, b):
    (p, e) = two_prod(a.hi, b.hi)
    e = fma(a.hi, b.lo, e)
    e = fma(a.lo, b.hi, e)
    e = fma(a.lo, b.lo, e)
    return normalize(p, e)

div(a, b):
    q0 = a.hi / b.hi
    r = fma(-q0, b.hi, a.hi)
    r = fma(-q0, b.lo, r + a.lo)
    q1 = r / b.hi
    return normalize(q0, q1)
```

Addition retains errors from both component sums to handle leading
cancellation. Multiplication keeps the low-by-low contribution. Division
uses one correction, with no input-dependent iteration. These algorithms
lose information in their rounded correction operations even when final
normalization is exact. The Df32 error analyses can be specialized with
`u = 2^-11` and an absolute underflow term based on `eta = 2^-24`; relative
`O(u^2)` behavior applies only when the required residuals have enough range.
It is not a guarantee near zero or after severe cancellation.

Pair-valued `mul_add` forms all four TwoProd decompositions,
combines the leading product with `c.hi` using TwoSum, and accumulates the
remaining terms into two fixed correction temporaries before normalizing:

```text
(p, e) = two_prod(a.hi, b.hi)
(s, t) = two_sum(p, c.hi)
(x, xe) = two_prod(a.hi, b.lo)
(y, ye) = two_prod(a.lo, b.hi)
(z, ze) = two_prod(a.lo, b.lo)
(h, l) = (e, 0)
for v in [t, c.lo, x, xe, y, ye, z, ze]:  # eight unrolled updates
    (h, error) = two_sum(h, v)
    l = l + error
(hi, lo) = two_sum(s, h)
return normalize(hi, lo + l)
```

This retains product information across cancellation instead of first
rounding an intermediate Df16 product. It does not promise IEEE-style
single rounding of the whole pair expression. Half residual underflow still
limits it. Benchmark the compensation cost and characterize errors before
replacing the sequence with anything cheaper. Square root and transcendental
functions are outside the initial scope.

## Special values and comparisons

Preserve the scalar leading infinity/NaN when error recovery would otherwise
introduce `infinity - infinity`. Clear the residual for nonfinite results.
Addition and FMA must also preserve overflow caused by a residual carry.
Multiplication preserves a nonfinite leading product. Division bypasses
refinement for a nonfinite leading quotient or an infinite divisor, avoiding
`infinity * zero` in its remainder.

Match Df32's FMA exception policy: finite-input leading product overflow is
terminal, even if a finite addend could have canceled it. For a nonfinite
addend, use scalar FMA classification so a true infinite addend is not
mistaken for cancellation of two input infinities. Invalid operations still
produce NaN. Do not promise floating-point exception flags or trapping.

Preserve input signed zeros, scalar signs for zero products/quotients, and
negative zero for `-0 + -0`; ordinary exact cancellation yields positive
zero. Negation flips both components and restores a positive-zero residual.
Use bit selects or short guards only where they serve these requirements;
do not classify every input defensively. The f16 zero-or-nonfinite bit test
is `((bits & 0x7fff).wrapping_sub(1)) >= 0x7bff` using `u16` arithmetic.

Normalized non-NaN pairs compare lexicographically by high then low, with
signed zeros equal. Implement `PartialEq` and `PartialOrd`, not `Eq`/`Ord`.
NaNs are unordered and unequal to all values. Never compare after collapsing
to f16 or by lexicographic raw bits.

## Public API and conversions

The `df16` module and `pub use df16::Df16` are gated with
`#[cfg(feature = "half")]`. Keep all primitive f16 references out of default
builds, including integration tests and benchmark entry points. Consumers
using primitive f16 syntax need their own nightly feature attribute; Cargo
feature activation does not set attributes in downstream crates.

The implementation mirrors Df32's core API: constants, `from_parts`, `to_parts`,
classification, comparisons, unary negation, arithmetic and assignment operators, and
`mul_add`. It implements `num_traits::{Zero, One, MulAdd, MulAddAssign}` for the
pair without requiring a primitive f16 `Float` implementation.

- `from_f16(x)` stores `(x, +0)` directly. `to_f16()` returns normalized `hi`.
- `from_f32(x)` splits `h = x as f16`,
  `l = (x - f32(h)) as f16`, then normalizes. Preserve `(h, +0)` when `h`
  is zero/nonfinite, and clear residuals on normalization overflow. For a
  finite nonzero `h`, residual rounding gives `abs(l) <= abs(h)`, permitting
  FastTwoSum here. Renormalization remains necessary at midpoint ties.
- `from_f64(x)` performs the same split directly in f64. Do not route through
  f32 and discard source detail before splitting. Neither split promises a
  universal exact scalar round-trip or nearest-pair rounding.
- `to_f32()` evaluates `f32(hi) + f32(lo)`, preserving a signed-zero high
  component explicitly. An unusually large component exponent gap can lose
  detail even though the ordinary pair precision is below 24 bits.
- `to_f64()` evaluates the sum in f64, with the same signed-zero rule.
  Every finite pair sum is exactly representable there: each component is
  a multiple of `2^-24` and a sum of two finite components has magnitude
  below `2^17`, requiring at most 41 significant bits.

Scalar conversions stay explicit and standalone. There are no wider-scalar
operation variants or hidden promotions of the pair arithmetic.

## Validation and performance plan

Tests require canonical outputs and consistent special-value behavior.
Arithmetic references use an exact integer lattice in units of `2^-24`;
even products of finite pairs fit in i128. Division compares `q*b` with `a`
on the product lattice. Tests measure the accuracy actually achieved rather
than applying Df32's application error threshold.

Implemented coverage exhausts scalar bit patterns and all finite midpoint
neighbors in f32/f64, checks full-range randomized normalization and
comparisons, and exercises special values, signed zeros, traits, layout,
residual carry, FMA cancellation, and residual underflow. Random arithmetic
uses high exponents -6 through +6 and signed residuals. Its conservative
regression tolerances are `2^-19` times input scale plus absolute underflow
terms (two component quanta for sums, sixteen for products/FMA). Division
uses `2^-18 * abs(a) + 4*eta*(1 + abs(b))` for the cross-multiplied error.
These bounds apply to the specified tests, not arbitrary inputs or chains.

Run tests and the benchmarks with:

```sh
cargo test
cargo +nightly test --features half
cargo +nightly test --release --features half
cargo +nightly clippy --all-targets --all-features -- -D warnings
cargo +nightly bench --features half
```

Host tests pass in debug and release with nightly Rust. The no-std library
also builds with `half` for `thumbv7em-none-eabihf`; this checks compilation,
not execution or performance on embedded hardware. Default stable builds
and benchmarks remain available without the feature.

Maintain the following coverage as the implementation evolves:

- Exhaust all 65,536 component bit patterns for scalar round trips,
  classification, and signed zeros; compare NaNs by classification.
- Test arbitrary component orders, midpoint parity, power-of-two boundaries,
  cancellation, residual carry, overflow, and subnormal transitions. Sweep
  f32/f64 inputs immediately below, at, and above every finite f16 midpoint.
- Check TwoSum reconstruction and TwoProd's conditional exactness. Include
  products whose residual underflows even though the leading product is
  normal, and compare both full TwoSum and any proven fast substitutions.
- Compare every operator against exact dyadic references; use rational or
  cross-multiplied bounds for division. A pair's exact f64 conversion does
  not make f64 an exact oracle for every product, FMA, or quotient.
- Characterize absolute and relative errors across exponent bands, exponent
  gaps, cancellation, and short chains. Exercise pair FMA against separate
  multiply/add, including underflow and leading overflow. Publish observed
  limitations without inventing a universal doubled-precision promise.
- Validate size/alignment, stable default builds, nightly `--features half`
  and `--all-features` builds, and no-std targets with appropriate f16 support.
  Enforce no allocation through runtime code and dependencies.

All three benchmarks include f16 and Df16 when `half` is enabled alongside
f32, f64, and Df32. Dependency chains use bounded round trips whose operands
remain meaningful in f16; timings are per iteration, with operation counts
printed by the harness. Independent bulk loops use preallocated outputs.
Conversion splits 10,000 f64 values in `[-1e3, +1e3]` into preallocated
slices, excluding allocation and generation from timing. This smaller
range prevents most half inputs from overflowing as they would at `1e6`.
Inspect native half/FMA instructions, widening, helper calls, register use,
spills, and buffer bandwidth. Packed half instructions do not automatically
accelerate these dependent correction sequences. Compare CPU and GPU results
separately; enabling the language feature does not establish device support
or a speedup over f32.

Backends that flush half subnormals can lose a residual far above high-part
underflow. Configure gradual underflow or explicitly validate a restricted
domain with no required subnormal intermediates. Do not silently change the
type's arithmetic contract across backends.
